# Contributing Guide

Adapted from gpui-kit `CONTRIBUTING.md`. Contributions are welcome: if you find
a bug or have an idea, please open an issue or submit a pull request.

Please ensure that you are using clean code, following the coding style and code
organization in existing code, and make sure all the gates pass (see
[Gates](#gates)).

Please submit **one PR that does one thing**; it helps us review your code more
easily and merge it fast.

## GPUI, GPUI Kit and this crate

This crate is built on gpui-kit and reaches GPUI only through it. gpui-kit pins
the `gpui-pre` snapshot crates to an exact version and a new snapshot reaches
applications only through a gpui-kit release (see gpui-kit `CONTRIBUTING.md`,
"GPUI and GPUI Kit").

So this repository:

- depends on `gpui-kit` through an exact requirement (git `rev` or `=x.y.z`);
- does not list `gpui-pre*` crates, except crates gpui-kit does not re-export,
  and then on the exact same snapshot version;
- moves to a new gpui-kit revision in a dedicated pull request that adapts the
  grid to any API change in the same pull request.

CI rejects anything else (`bun script/check-gpui-kit-pin.ts`).

Changes that belong in gpui-kit or GPUI are contributed there, not patched here.

### A local gpui-kit checkout

`Cargo.toml` pins gpui-kit to a git revision, so the first build needs network
access to GitHub; after that cargo builds from its git cache, offline too. To
build against a local gpui-kit checkout instead (with no network at all, or to
try a gpui-kit change), clone gpui-kit next to this repository and create
`.cargo/config.local.toml`:

```toml
[patch."https://github.com/longbridge/gpui-kit"]
gpui-kit = { path = "../gpui-kit/crates/kit" }
```

The tracked `.cargo/config.toml` includes that file when it exists, and
`.gitignore` keeps it out of commits. The path is relative to the repository
root, and the patch covers `crates/grid-web` too. Check out the pinned revision
(`git -C ../gpui-kit checkout <rev>`, the `rev` in `Cargo.toml`) to build what
CI builds.

While the patch is active, cargo records gpui-kit's crates in `Cargo.lock` and
`crates/grid-web/Cargo.lock` as path packages (their `source` lines go away), so
`--locked` fails and the pin check warns. Never commit those lines: CI builds
the pinned revision with `--locked` and rejects them. Before a commit, drop them
with `git checkout -p Cargo.lock crates/grid-web/Cargo.lock`, or move the file
aside and run `cargo metadata --format-version 1 > /dev/null` to rewrite the
entries from the pinned revision.

The web build (`crates/grid-web`) also reads a few gpui-kit icons from
`../gpui-kit`, so it needs that checkout, at the pinned revision, either way.

## AI-Assisted Contributions

We welcome contributions written with AI, including pull requests where 100% of
the code was generated by AI. What matters is whether the change is thoughtful,
focused and well validated. The contributor is always responsible for the final
result.

Before opening a pull request, please make sure that:

- The problem is real and the change is necessary.
- The API and implementation follow the existing patterns of GPUI, GPUI Kit and
  this crate.
- UI changes follow GPUI Kit's visual and interaction conventions (Design Guides).
- The code has been reviewed by you and properly tested. Run the affected
  examples; screenshots or recordings are encouraged for UI changes.
- A pull request focuses on one thing and keeps the diff as small as practical.
  When using AI, ask it to avoid unrelated refactors, cleanup, or formatting.
  **Less is better.**
- AI-generated portions are marked in the pull request.

### Describe public API changes

A pull request that adds, changes or removes anything public (a type, a
function, a builder method, an action, a re-export) lists it in the description
under a `## Public API` section, with the signature as a reviewer would read it
in the docs. Say what each item is for in one line; a name alone is not enough.

Changes to existing public items go under `## Breaking Changes` with a `diff`
block showing the old and the new usage, even when the old form still compiles.
Additive changes are not breaking, but they are still listed.

### Describe performance impact

A pull request that touches ingestion, the projection engine or painting adds a
`## Performance` section: the benchmark or profile before and after, with the
load profile (rows, updates per second, grids open).

## Gates

Every gate below runs in CI (`.github/workflows/ci.yml`) and must pass locally
before a pull request:

| Gate | Command | CI |
|---|---|---|
| Typos | `typos` | Linux |
| GPUI only through a pinned gpui-kit | `bun script/check-gpui-kit-pin.ts`, and again with `crates/grid-web/Cargo.toml` | Linux |
| Format | `cargo fmt --all --check`, and in `crates/grid-web` | Linux |
| Unused dependencies | `cargo machete` | Linux |
| Clippy, warnings denied, all targets | `cargo clippy --workspace --all-targets --features gpui-kit-grid/test-support -- --deny warnings`, and again with `gpui-kit-grid/decimal` and with `gpui-kit-grid/derive` added | Linux |
| The library without features | `cargo check -p gpui-kit-grid` | Linux |
| Docs, warnings denied | `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --features gpui-kit-grid/decimal,gpui-kit-grid/derive` | Linux |
| Tests (unit, property, headless UI) | `cargo test --workspace --features gpui-kit-grid/test-support`, and again with `gpui-kit-grid/decimal` and with `gpui-kit-grid/derive` added | macOS, Linux, Windows |
| Doc tests | `cargo test --workspace --features gpui-kit-grid/test-support --doc` | macOS |
| The library for the browser | `RUSTC_BOOTSTRAP=1 cargo check -p gpui-kit-grid --lib --target wasm32-unknown-unknown --features decimal,derive` | Linux |
| The web examples | `RUSTC_BOOTSTRAP=1 cargo clippy --workspace --target wasm32-unknown-unknown -- --deny warnings` in `crates/grid-web` | Linux |
| Examples, release build | `cargo build --release -p gpui-kit-grid --examples` | Linux |

`Cargo.lock` and `crates/grid-web/Cargo.lock` are committed, and every cargo
call in CI adds `--locked`. With a local gpui-kit patch, run the gates without
`--locked` (see [A local gpui-kit checkout](#a-local-gpui-kit-checkout)).

The documentation site has its own workflow (`.github/workflows/site.yml`):
`bun run --cwd site check`, `bun run --cwd site build` and
`bun test --cwd site`, after a release build of the web examples
(`make -C crates/grid-web build`).

## Code Style

Before you start to write code, please read the existing code and
[AGENTS.md](AGENTS.md) to follow the same coding style and code organization.

- Refer to existing code or to macOS/Windows controls API design to name your
  functions, properties and structs.

## Development and Testing

### System dependencies

```bash
./script/bootstrap
```

The site (`site/`) also needs Node 22.23.4 or newer, Astro's minimum
(`.nvmrc`, which nvm and fnm read), and Bun.

For Windows, run in PowerShell:

```powershell
.\script\install-window.ps1
```

### Accessibility-driven UI testing

When manual verification is needed for focus, keyboard, selection, menu, or
input behavior, use accessibility-driven interaction by default, as described in
gpui-kit `docs/ACCESSIBILITY-UI-TESTING.md`.

### Reviewing UI changes

When reviewing a UI or interaction change, check whether the UI tests exercise
the behavior claimed by the pull request, including its relevant states and
edge cases. If coverage is missing, describe the specific gap. Ask for a focused
manual check only when automated UI tests cannot exercise that scenario.

## UI Guides

Follow gpui-kit's Design Guides. gpui-kit is inspired by macOS and Windows
controls, combined with shadcn/ui design.

### Rules

- Use the `default` mouse cursor, not `pointer`, unless it's a link; we are
  building desktop apps, not web apps.
- Use the `md` size for most cases and as the default.

## Releases

The library and the site are released separately, each on its own tags.
Changes pile up on `main` through pull requests; a tag cuts a release.

| | Tags | What a tag does |
|---|---|---|
| The library | `vX.Y.Z` | CI runs on the tag; once every job passes, its Release job checks that the tag names the crates' version and that the site's install snippets name the tag, scans the history for secrets and opens the GitHub release (the repository's latest) with the `Cargo.toml` lines to use. Not on crates.io yet: the crate depends on gpui-kit by git revision. |
| The site | `site-vX.Y.Z` | `.github/workflows/site.yml` scans the history for secrets, publishes the image `ghcr.io/giglabocom/gpui-kit-grid-site` (`X.Y.Z`, `X.Y`, `X` from 1.0, `latest`; amd64 and arm64), deploys to Cloudflare and opens a GitHub release with the site's commits since its last tag. |

### The library

Versions follow semver: the public API of `gpui-kit-grid`,
`gpui-kit-grid-feed` and `gpui-kit-grid-macros` (and the gateway binary,
which ships with them) share one version.

1. In a pull request, set `version` in `crates/grid`, `crates/grid-feed`,
   `crates/grid-macros` and `crates/grid-gateway` (`Cargo.toml`), let cargo
   update both lock files (`Cargo.lock`, `crates/grid-web/Cargo.lock`), and
   name the new tag in the install snippets
   (`site/src/content/docs/start.md`, `guides/columns.md`).
2. Merge it, then tag that commit of `main` and push the tag:

   ```bash
   git tag -a v1.0.0 -m "gpui-kit-grid 1.0.0" origin/main
   git push origin v1.0.0
   ```

A wrong tag fails the Release job before anything is published; delete it
(`git push origin :refs/tags/v1.0.0`), fix, and tag again.

### The site

The site is the pages, the live demos and the API reference, so a change
under `crates/` reaches it as well as one under `site/`.
`script/release-site` reads the paths the site workflow builds on, lists
the commits there since the last site tag and makes the tag; with nothing
new for the site it makes none:

```bash
script/release-site                 # the site's changes since its last release
script/release-site 0.2.0 --push    # tag site-v0.2.0 at origin/main and push it
```

A pull request and `main` build the image and try it (`docker/site/smoke.sh`)
without publishing it. Run by hand, the Site workflow publishes the image of
any ref as `edge`; only a tag moves `latest` and the deployed site.

The demos' recordings (the wiki's replay, the ships' and Helsinki's
fallback) are not committed: the Site workflow downloads them from the
release `site-recordings-1` and checks them against
`script/site-recordings.sha256`. Without that release the site goes out
without them, with a warning.

## Profile the performance

When you change rendering, ingestion or the engine, profile it:

```bash
MTL_HUD_ENABLED=1 cargo run -p <example>   # macOS Metal HUD
samply record cargo run -p <example>       # sampling profiler
```
